============================================================
  Experiment A — 70/30 IO/CPU  |  FIFO
============================================================
  Policy            : FIFO
  IO ratio          : 70% IO / 30% CPU
  Tasks completed   : 1000 (299 CPU + 701 IO)
  Makespan          : 39188.0 ms  (39.2 s)
  Avg wait time     : 8979.1 ms
  Max wait time     : 18461.3 ms
  Avg turnaround    : 9179.7 ms
  Avg CPU usage     : 89.5%
  Avg active workers: 5.12 / 8
  Peak queue length : 465
 
  Interpretation:
  FIFO keeps CPU usage high (89.5%) but at the cost of extreme wait times.
  Avg wait of 8979 ms and max wait of 18461 ms show that tasks stuck behind
  CPU-task clusters can wait nearly 18.5 seconds before being dispatched.
  Peak queue length of 465 shows significant backlog during CPU-heavy bursts.
  Head-of-line blocking is the root cause: when 2 CPU tasks are running
  (70% CPU used), a third CPU task at the queue head blocks all queued IO
  tasks even though 30% CPU budget remains available.
 
============================================================
  Experiment B — 70/30 IO/CPU  |  Optimized
============================================================
  Policy            : Optimized
  IO ratio          : 70% IO / 30% CPU
  Tasks completed   : 1000 (299 CPU + 701 IO)
  Makespan          : 41912.6 ms  (41.9 s)
  Avg wait time     : 5232.7 ms
  Max wait time     : 21178.4 ms
  Avg turnaround    : 5433.3 ms
  Avg CPU usage     : 83.8%
  Avg active workers: 4.80 / 8
  Peak queue length : 283
 
  Interpretation:
  Optimized reduces avg wait time by 3746.4 ms (41.7%) vs FIFO. Peak queue
  length drops from 465 to 283. However, makespan is 2.7 s longer than FIFO.
  The two-queue design improves responsiveness — individual tasks wait much
  less — but the CPU-first dispatch adds overhead that slightly increases
  total wall-clock time. This is a real trade-off: throughput (makespan) vs
  responsiveness (wait time).

  CPU utilisation gain : -5.7%                 [FIFO higher raw CPU%]
